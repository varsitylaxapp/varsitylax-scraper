## 1. Staged switch-on

### What switching on does to production

| State | Pages | First commit | Kickoff times that appear in the app | Second run |
|---|---|---|---|---|
| MT | 6 | update 44, insert 0 | 44 games | ratings only (6 reads), no change |
| NV | 15 | update 118 | 119 games | same |

| ID | 31 | update 167 | 179 games | same |
| WA | 75 | update 0 | 2 (cross-border) | same |

- **The visible change:** `datetime` goes from null to a value on 434 games (1,334
  appearances across the API). No existing time changes. No game is inserted or deleted.
  Each state's first commit adds 1–2 `source_conflicts` rows.
- **Washington writes no game.** It adds about 484 `game_source_records` and about 108
  `source_conflicts` rows (111 conflict fields on 104 games), because WHSBLA stays
  canonical. Those rows feed plan 3.
- **Unresolved names: 0 in every state.**
- **Request load once on:** each run reads the 6 ratings feeds. The first run after
  Pacific midnight (08:00 UTC) also re-reads every page of every state that is on.
  With all five on, that's about 150 reads of the 160 cap, at 2 s apart, so about 5
  minutes added to that one run. Other runs add about 12 s.
- **Season:** the 2026 season is over, so live pages should be close to the recordings.
  The reasons to switch on now are the kickoff-time backfill and proving the job before
  2027.

### Each stage changes one Railway variable, so it makes a new cron deployment

Every variable change redeploys `varsitylax-cron`. Since 2026-11-16 the cron leaves from
static outbound IPs (162.220.232.251, 152.55.176.240, 152.55.177.181; RELEASE.md), so a
deploy no longer rolls the dice on a blocked host. Each stage still does the short
RELEASE.md after-deploy check: the first run logs one of the three IPs and `✓` on all
six states. A 403 or an unknown IP stops the stage; there is no redeploy-and-retry step
any more.

One remaining risk: the three IPs are **shared** with other Railway customers. If
Cloudflare ever challenges one of them, every run fails, not one deployment. The health
endpoint (plan 2, and the existing `/api/v2/health/laxnumbers`) is what would catch it.

### Stop conditions (approved; stop the stage, report, change nothing else, turn nothing off and undo no data without asking)

- Any `insert` > 0, any stale mark, any identity conflict, or `unresolved` > 0.
- An update count more than 10% off the table.
- Any `✗`, a 403 included, or an outbound IP that isn't one of the three.
- The payload compare fails.
- The game count moves.

### Turning it off

- **Off:** delete `LAXNUMBERS_GAMES_STATES` (leave or delete `COMMIT`). That redeploys
  the cron, so the short after-deploy check applies. The next run logs
  `[LaxNumbers games] off (LAXNUMBERS_GAMES_STATES unset)` and makes no request.
- **Drop one state:** set `STATES` to the remaining list.
- **Data written stays.** The times are correct data. Undoing a stage's data is a
  separate prod write that needs its own approval:
  - set `game_datetime` back to NULL for that stage's snapshot ids;
  - delete the `source_conflicts` and `laxnumbers` `game_source_records` rows above the
    snapshot max ids;
  - delete that state's `laxnumbers_teams` rows.
- **Do not use `COMMIT=0` as an off switch.** A dry run left on reads up to 40 pages
  every 2 hours.

## 2. Game-job health

### Gap

- `/api/v2/health/laxnumbers` counts only `laxnumbers` / `laxnumbers-v2` rows, so the
  game job's failures are invisible to it.
- An IP block would show there anyway: the ratings fetch fails first, in the same run.
- A failure that belongs to the game job alone would not show anywhere except the
  cron log. Examples: a changed page layout, a DB error mid-import, or the cap
  starting to bite.

### Plan (diff 9b)

- **New function `gamesHealth`** in `src/scrape-health.js`:
  - source `laxnumbers-games`;
  - the same `consecutiveFailures` rule and THRESHOLD 3;
  - the same public-body rule: no error text, only times and the HTTP status.
- **New endpoint `GET /api/v2/health/laxnumbers-games`**, kept separate so the existing
  endpoint and its future monitor keep their meaning. 503 when any state has 3 or more
  failed committing runs in a row; otherwise 200. Per state it returns:
  - `consecutiveFailedRuns`, `lastSuccessAt`, `lastErrorAt`, `lastErrorHttpStatus`;
  - flags that warn without failing:
    - `overCapLastRun` (capped > 0);
    - `unresolvedLastRun` > 0;
    - `missedDailyPass` (no row in the last 26 h, though the state had rows in the
      last 7 days).

  The flags are parsed from the fixed summary text with one strict pattern; a row
  that doesn't match gives null, never text.
- **Which states:** every state with a `laxnumbers-games` row in the last 7 days. The
  API can't see the cron's variables, so "off" and "stopped" look the same. That's why
  staleness is a flag, not a 503.
- **Dry runs write no rows,** so stage 0 is checked from the log only. That is
  intended.
- **Tests:** pure-function tests like the existing ones. A staging proof with seeded
  rows covering 0, 2 and 3 failures, a stale state, and an over-cap row.
- **Deploy:** API only. No migration and no cron change, so no new IP risk.
- **Monitor:** the first UptimeRobot monitor, on `/api/v2/health/laxnumbers`, is already
  set up and green. Spencer adds the second one, on the new endpoint, after 9b is deployed. Both endpoints will fire on an IP block. With static IPs,
  that is now the main 403 risk: a challenge on a shared IP fails every run until it
  clears, not just one deployment. That's acceptable; the alternative is hiding a
  game-job 403 behind the other one.

**Order:** ship 9b before stage 1, so committing runs are monitored from their first
row.

### Option not recommended

Have the job write an `off` row each run so "off" becomes visible. Diff 8 promises that
off opens no connection, so this would change that promise.

## 3. Ruling workflow

**Approved in direction; diff 9c comes after the switch-on,** once the Washington
source_conflicts rows exist to feed it. Rulings stay Spencer's: nothing in 9c may decide an
alias, a merge or a game identity on its own.

### Problem

Human decisions are spread across four files:

- `data/whsbla-2026/alias-decisions.json`: decisions, merges, do_not_merge,
  display_renames, game_identity_rulings, roster_admissions;
- `data/foreign-row-rulings.json`;
- `data/ruled-out-games.json`;
- `data/team-timezones.json`.

Rulings are made when something surfaces, and each one has needed its own apply step
(the Claremont alias went through window 6). Switch-on adds about 110 Washington
conflicts.

### Plan: one queue, the same five steps every time

1. **Inbox (diff 9c, read-only):** `scripts/rulings-inbox.js` reads prod inside a
   rolled-back transaction and writes
   `~/Desktop/varsitylax/patches/rulings-inbox-<date>.csv`. One row per open item, with
   a kind, the games affected, first and last seen, context, and machine suggestions in
   a column marked *suggestion, not a ruling*. Kinds:
   - `unresolved_aliases` with no `resolved_team_id`;
   - `source_conflicts` with no ruling;
   - identity conflicts;
   - foreign rows that were refused.
2. **Decide:** Spencer fills one column per row with one of:
   - `resolve:<slug>`;
   - `not-a-team`;
   - `ask-league` (Washington goes to Brandon as the existing conflicts CSV);
   - `defer`.

   Only Spencer's column counts.
3. **Record:** each decision goes into the file for its kind, in the existing shape:
   approver, approved_on, basis, evidence. One commit per batch: "Rulings <date>: N
   items, approver Spencer". This **is not docs-only**, because the next import reads
   these files, so it goes through diff review.
4. **Apply:** where a ruling needs a database row (`team_aliases`,
   `unresolved_aliases.resolved_team_id`), an apply script does it. It works like
   `window6-data.js`: dry run by default, `--commit` refused against prod without its
   flag, and a payload compare. Rulings that only the import reads (foreign rows,
   ruled-out games) take effect on the next run.
5. **Verify:** re-run the inbox and check the items are gone. The state's next
   `laxnumbers-games` row goes from `partial` to `success`.
